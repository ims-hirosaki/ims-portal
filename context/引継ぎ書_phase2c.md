## 問題1：重複ガードと「1日1件」制約が同時リクエストで破れる

PunchService::punch() は「SELECT で確認 → INSERT」の間に隙間があり、
2つのリクエストがほぼ同時に到達すると、両方が
has_recent_punch()=false / validate_transition()=OK を見て
両方とも INSERT に到達します。

ダブルタップ、通信が遅いときの連打、2タブ同時操作で現実に発生します。

重複ログが1件増えること自体より、clock_in が同一 work_date に
2件入り得ることが問題です。この「1日1件」制約は DDL に UNIQUE を張らず
アプリ層で担保する設計にしたため、ここが唯一の防波堤です。
2d の休憩補完・2e の打刻修正はこの制約を前提に組むので、
今のうちに塞いでください。

### 対処

punch() の判定〜INSERT の全体を、ユーザー単位の排他で囲んでください。
スキーマ変更が不要な MySQL の名前付きロックを使います。

- ロック名は user_id ごとに分ける（例：ims_punch_{user_id}）
- タイムアウトは 3 秒程度
- ロックが取得できなかった場合は duplicate として 409 を返す
  （連打時の挙動として自然なため）
- 解放は必ず finally で行い、例外時も残らないようにする
- ロック取得・解放は Repository 側にメソッドとして置き、
  PunchService からは業務的な名前で呼べるようにしてください
  （PunchService に SQL を持ち込まない）

トランザクション + SELECT ... FOR UPDATE でも実現できますが、
2d でトランザクションを本格導入するまでは名前付きロックのほうが
単純で読みやすいと判断しています。異論があれば実装前に指摘してください。

## 問題2：日付をまたぐシフトで退勤できない

PunchService::resolve_work_date() の最後の分岐に穴があります。

    $open = Repository::open_shift_date($user_id, $today);
    if ($open !== null && ($open === $today || $open === $boundary_date)) {
        return $open;
    }
    return $boundary_date;

### 再現（既定設定 date_boundary_hour = 0）

22:00 出勤 → 翌 01:00 退勤

- $hour(1) < $boundary_hour(0) は不成立 → $boundary_date = 翌日
- 開いている勤務は前日 → $open === $today も
  $open === $boundary_date も両方 false
- work_date は翌日に決まる
- 翌日のログは空なので validate_transition() が not_clocked_in を返し、
  「まだ出勤打刻がありません」となって退勤できない

境界時刻を 4 時にした場合も同じ形の穴が残ります。
22:00 出勤 → 翌 05:00 退勤で、$hour(5) >= 4 のため $boundary_date は翌日、
開いている勤務は前日 → 一致せず → 退勤不能。
つまりシフトが境界時刻をまたいで終わると常に破綻します。

### 対処

$open === $today || $open === $boundary_date という日付一致の条件は、
「何日も前の閉じ忘れた勤務に誤って紐づけない」ための安全弁だと理解しています。
意図は妥当なので条件自体は残しつつ、判定基準を変えてください。

日付の一致ではなく、開いている勤務の clock_in からの経過時間で判定します。

- 「直近 N 時間以内に始まり、まだ閉じていない勤務」があれば、そこにぶら下げる
- N は 18〜24 時間程度を想定
- これなら日付をまたいでも拾え、1週間前の閉じ忘れは拾わない

N の置き場所（定数か Settings か）は、2d のケースB（休憩6時間超の判定）と
関連するため、2d の設計と整合する形を提案してください。
2c 時点では定数で構いませんが、判断の理由をコメントに残してください。

open_shift_date() の探索範囲も、この判定に合わせて見直しが必要か確認してください。
