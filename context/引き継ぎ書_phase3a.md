## 2. 確定済みアーキテクチャ方針（詳細は 08_implementation_guidelines.md）

- **モジュラーモノリス**：単一プラグイン内にモジュールディレクトリ。分割しない。
- 業務ロジックは**すべてプラグイン側**。テーマには置かない。
- トランザクションデータは**独自テーブル**。カスタム投稿タイプは使わない。
- コアはモジュールに依存しない。モジュール側が**フック経由で自己登録**する。

### 実装で判明したコード規約（08 の記載と実装が食い違う点。**実装に合わせること**）

- `Router::register()` はスラッグ文字列のみを取る。フックに渡ってくるのはクラス名の文字列。
- `TileRegistry::add()` の `caps` は capability 名。ロール名ではない。
- コアの `Assets` はモジュール固有CSS/JSを読み込まない。各モジュールが自前 enqueue する。
- `ims-portal.php` の `boot()` が各モジュールの `Bootstrap::init()` を直接呼ぶ（コア無改修の唯一の例外）。
- REST の nonce はコアが検証する（`imsPortal.nonce`・`X-WP-Nonce`）。
- **`Router::is_portal_request()` は「/portal/配下かどうか」、`Router::is_dashboard_request()` は「ダッシュボードトップかどうか」を返す。**
  ダッシュボードのクエリ変数値は内部的に `'__dashboard__'`（空文字ではない）なので、モジュール側でこの文字列を直接比較してはいけない（2gで実際に踏んだバグ。§10参照）。
- **ロール名ではなく必ずカスタム権限（capability）で判定する。** `approver` と `general_staff` を区別する必要が生じた場合も、新しい capability を `Roles::CAPABILITIES` に追加する（2eで `ims_correct_own_punch` を追加した前例あり）。

## 5. モジュール02の設計判断まとめ（次の実装者が知っておくべきこと）

### 責務の分け方（全スライス共通）
- **`RestController`** … HTTP だけ。
- **`PunchService`** … 業務判断の唯一の置き場。ダッシュボード連携（`dashboard_summary()`）も含め、判定はすべてここに集約し、UI側とAPI側で二重実装しない。
- **`StatusCalculator`** … DB/WPに触れない純粋ロジック。テストはここに書く。
- **`Repository`** … SQLだけ。テーブル名は必ず `Schema::logs_table()` 等を経由する（`Repository`自身にはこれらのメソッドは無い）。

### 2d：休憩補完付き退勤
- ケースA（休憩中→退勤）：最終`break_in`からの経過分数を選択。
- ケースB（休憩0件・6h超→退勤）：開始・終了の**時刻そのもの**を入力（ケースAは既存の`break_in`が起点だが、ケースBはそもそも存在しないため）。
- 労基法の閾値（6h/8h/45分/60分）は `PunchService` の public const。JS側には数値を持たせず `wp_localize_script` で渡す。

### 2e：打刻修正
- 新設 capability `ims_correct_own_punch`（general_staff/hr_admin/administrator。approverには付与しない）で、ロール名分岐を避けた。
- 締め後ロック（`MonthlyClosing::is_locked()`）は**すべての操作者に優先して**効く。03実装時にここへ実データ参照を接続する（現状は常に false）。
- 整合性チェック（`StatusCalculator::is_chronologically_consistent()`）は、**当日がまだ完了していない場合**（末尾が`break_in`や`clock_in`のみ）を矛盾と誤判定しないよう注意。一度ここでバグを出した（§10）。

### 2f：打刻ログ照会
- 管理者（`ims_manage_users`）は他人のログも修正可能。`PunchService::correct_punch()` の所有者チェックはこれを踏まえて分岐している。
- `Repository::search_logs()` は監査画面の暴走防止のため既定500件でLIMITし、`total`（LIMIT適用前件数）も返す。

### 2g：ダッシュボード連携
- `PunchService::dashboard_summary()` に判定を集約（ステータスカード・タイルバッジ・summary APIの3箇所が同じ関数を見る）。
- 03・05が未実装のため、ステータスカードは現状モジュール02単体表示。複数モジュールが横並びで寄与するようになったときの行レイアウトの持ち方（各モジュール／core）は**未解決の設計課題**として残っている。03の統合時に検討すること。

## 9. 作業の進め方（この会話で確立した進行様式）

1. **要件定義書を先に精読**してから実装する（コードより要件が正本）。
2. **1機能を細かくスライス**。特に書き込みを伴う処理は単独スライスにする（例：2d-1バックエンド／2d-2フロントエンドの分離）。
3. 設計判断に曖昧さがある場合（要件定義書に明記がない、既存の権限モデルと整合しない等）は、**実装前にユーザーに確認する**。このセッションでは複数回、AskUserQuestionで確認してから進めた（例：2eのcapability追加方針、2fの検索上限）。
4. 実装後は必ず**全ファイル`php -l`**、ロジックは**スモークテスト**を書いて通す。
5. **`php -l`は構文エラーしか検出できない。** `self::method()`が実際に存在するかまでは検証しないため、このセッションで2回、存在しないメソッド呼び出し（`Repository::logs_table()`等）を本番まで届けてしまった。次の実装者も、ReflectionClassで`self::`呼び出しの実在を検証する簡易スクリプトを書いて実行することを推奨する。
6. デプロイは**commit → `main`にPR経由でマージ**（このセッションでは全てPRを作成してユーザー承認を得た上でマージしてもらった）。
7. **一度マージされたブランチは再利用しない。** 同じブランチ名で作業を続ける場合、`git fetch origin main && git checkout -B <branch> origin/main`でmainから作り直してから次のコミットを積む。
8. 既存実装を触るときは**依頼された箇所だけ**。共有CSS/JSは画面スコープで回避し、**新規ファイルを作る前に同名ファイルが既に無いか必ず確認する**（§10のインシデント参照）。

## 10. 既知の申し送り・重要インシデント（次の実装者への注意）

このセッションで実際に発生した事故・バグとその教訓。同じ轍を踏まないよう共有する。

1. **既存ファイルの誤上書き（2f）：** 新規管理画面用CSSを`timecard-admin.css`という名前で作成しようとしたところ、その名前は既に2aの打刻システム設定画面が使用中のファイルだった。一度上書きしてしまったが、コミット前に`git status`で気づき、`git show <commit>:<path>`で復元した。**教訓：新規ファイルを作る前に必ず`ls`または`git status`で既存ファイルの有無を確認する。Writeツールは「新規作成」でも、対象パスが既存ファイルと衝突していないかは別途確認が要る。**
2. **`self::`の存在しないメソッド呼び出し（2e・2f）：** `Repository`クラス内で`self::logs_table()`/`self::corrections_table()`と書いていたが、これらは`Schema`クラスのメソッドだった。`php -l`では検出できず、本番の「打刻ログ照会」画面で実際にFatal errorが発生してから発覚した。**教訓：クラスをまたぐメソッド参照は`self::`ではなく必ずクラス名で明示する。可能なら実装後にReflectionベースの静的チェックを走らせる。**
3. **ダッシュボードのクエリ変数の思い込み（2g）：** `Router`のダッシュボード判定で、クエリ変数が空文字になると思い込んで`get_query_var('ims_portal_page') !== ''`という条件を書いたが、実際の内部値は`'__dashboard__'`だった。ステータスカードのCSSが一切読み込まれず、無地のテキスト表示になっていた。**教訓：他クラスの内部実装（定数化されていない文字列等）に依存する条件を書く前に、必ずそのクラスの実装を読んで確認する。** この際、`Router::is_dashboard_request()`という正式な公開メソッドを追加し、モジュール側が内部文字列を直接見なくて済むようにした。
4. **整合性チェックが「未完了の1日」を矛盾と誤判定（2e）：** `is_chronologically_consistent()`が「休憩中のまま（まだ退勤していない）」状態を矛盾と誤判定し、進行中の勤務日の打刻修正が一切できなくなっていた。**教訓：状態遷移の途中経過（現在進行形の状態）を、完了済みデータの検証ロジックでチェックする際は、「まだ終わっていないだけ」のケースを矛盾ケースと混同しないよう明示的にテストケースを用意する。**

いずれも実機での動作確認によって発見・修正済み。**「php -lが通った」「スモークテストが通った」は動作保証の一部でしかなく、実機確認まで含めて初めて完了とする**、という03以降でも徹底すべき教訓。
