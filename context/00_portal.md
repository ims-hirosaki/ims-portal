# 要件定義書：00_ポータルサイト基盤モジュール (00_portal.md)
 
## 1. 目的・概要
 
本モジュールは、IMS Hirosaki 社内業務システム全体の**フロントエンドポータル基盤**を定義する。01〜05 の各業務モジュールが提供する機能を、統一されたUIの下に束ね、社員が一つのエントリポイントから迷わず各機能にアクセスできる環境を整えることを目的とする。
 
本モジュールは「機能」を持つというより、**ポータル全体に共通するレイアウト・ナビゲーション・アクセス制御・UI規約** を定義する「基盤」としての役割を担う。各業務機能の要件は 01〜05 の各モジュールで定義済みであり、本モジュールはそれらを包む「外側の器」に相当する。
 
### 設計方針
 
- **対象ユーザー：** `general_staff`・`approver` 権限の一般社員・承認者（管理者は wp-admin を使用するため、ポータルは一般社員・承認者向けに絞る）
- **UI スタイル：** タイル型ホーム画面＋ヘッダーナビの組み合わせ
- **デバイス：** PC をメインターゲットとし、スマートフォンでの打刻など限定的な操作にも対応するレスポンシブ設計
- **ポータル内通知：** 最小限（主要な通知は Google Chat に委譲し、ポータルにはバッジ表示のみ）
- **ダッシュボード：** 全権限共通の基本レイアウトに、権限別ウィジェットを追加表示する構成
---
 
## 2. URL 構造（全モジュール共通定義）
 
本モジュールが `/portal/` 配下の URL を統括管理する。各 URL の実装は対応するモジュールが担うが、URL 体系の正規定義は本モジュールに集約する。
 
| URL | 画面名 | 実装モジュール | 対象権限 |
|---|---|---|---|
| `/portal/login/` | ログイン画面 | 01_ユーザー管理 | 全員（未認証） |
| `/portal/` | メインダッシュボード（ホーム） | **本モジュール** | 全認証ユーザー |
| `/portal/profile/` | マイページ | 01_ユーザー管理 | 全認証ユーザー |
| `/portal/timecard/` | 打刻コンソール | 02_打刻管理 | `general_staff`・`approver` |
| `/portal/attendance/` | 月次勤務表・勤怠入力 | 03_勤怠管理 | `general_staff`・`approver` |
| `/portal/expenses/` | 交通費・借上げ入力 | 04_交通費 | `general_staff`・`approver` |
| `/portal/approval/` | 申請・承認 | 05_稟議 | `general_staff`・`approver` |
 
> **URL 追加ルール：** 新しい業務機能を追加する場合、`/portal/{機能名}/` の形式で本テーブルに追記し、本モジュールのルーティング設定に反映することを必須とする。

## 3. 画面要件（UI/UX）
 
### 3.1. 共通レイアウト構造
 
ポータル全画面に共通する 2 層構造を採用する。
 
```
┌──────────────────────────────────────────┐
│  ヘッダー（固定）                          │
│  [IMS ロゴ] [ページタイトル]  [ユーザー情報]│
└──────────────────────────────────────────┘
┌──────────────────────────────────────────┐
│                                          │
│  コンテンツエリア（各ページの内容）         │
│                                          │
└──────────────────────────────────────────┘
```
 
**ヘッダー仕様：**
 
- **左：** IMS Hirosaki ロゴ（クリックで `/portal/` へ遷移）
- **中央：** 現在のページタイトル（例：「打刻」「月次勤務表」）
- **右：** ログインユーザー名 ＋ バッジエリア（→ 3.3 参照）＋ ログアウトボタン
- ヘッダーはスクロール時も画面上部に固定（`position: sticky`）する。
- スマートフォン表示時はロゴとバッジエリア・ユーザー名のみ表示し、ページタイトルを省略する。

```
┌──────────────────────────────────────────┐
│  ヘッダー（固定）                          │
└──────────────────────────────────────────┘
┌──────────────────────────────────────────┐
│  [Gmail] [Drive] [Chat] [Cal] | [Teams]  │  ← 外部ツールランチャー
└──────────────────────────────────────────┘
┌──────────────────────────────────────────┐
│  [勤務ステータス] [今月の勤怠] [申請・承認]  │  ← ステータスカード
└──────────────────────────────────────────┘
┌──────────────────────────────────────────┐
│  [打刻] [勤務表] [交通費] [申請] [マイページ]│  ← 機能タイルグリッド
└──────────────────────────────────────────┘
```
 
#### 3.2.1. 外部ツールランチャーエリア
 
ヘッダーの直下・ステータスカードの上に配置する白地カード型のランチャーエリア。**ダッシュボード（`/portal/`）にのみ表示し、他のポータルページには表示しない。**
 
**配置・表示仕様：**
 
- 白地・薄いボーダーのカード型コンテナにツールアイコンを横並びで表示する。
- アイコンサイズは 32px × 32px。ツール名を下部にキャプション表示する。
- Google 系ツールと Microsoft Teams の間に区切り線を入れる。
- ホバー時に軽い浮き上がりアニメーション（`transform: translateY(-2px)`）を適用する。
- **スマートフォン（640px 以下）では非表示にする。**（理由：OS の通知センターとのスワイプ競合回避、外部ツールは PC での利用が主体）
- 登録ツールが 0 件の場合はランチャーエリア自体を非表示にする。
**設計方針：**
 
- iframe による埋め込みは対象ツールすべてが `X-Frame-Options` / CSP により技術的に不可能なため、採用しない。
- リンクはすべて `target="_blank" rel="noopener noreferrer"` で**別タブ**として開く。
- 全ユーザーに全登録ツールのアイコンを表示する（認証方式による出し分けは行わない）。
- 表示するツール一覧・順序・アイコンはすべて `wp_ims_launcher_apps` テーブルから取得し、管理者の設定変更が即時反映される。
**初期登録データ（システム導入時のデフォルト）：**
 
| 表示順 | ツール名 | 遷移先 URL | プロトコルスキーム |
|---|---|---|---|
| 1 | Gmail | `https://mail.google.com/` | なし |
| 2 | Drive | `https://drive.google.com/` | なし |
| 3 | Chat | `https://chat.google.com/` | なし |
| 4 | カレンダー | `https://calendar.google.com/` | なし |
| 5 | Teams | `https://teams.microsoft.com/` | `msteams://` |
 
> 初期データはプラグイン有効化時のマイグレーション処理で自動投入する。
 
> **アイコン素材の利用規約：** Google ブランドアイコンは Google Brand Resource Center、Microsoft アイコンは Microsoft Brand Central の利用規約に従い使用すること。アイコンの改変（色変更・変形等）は禁止されているため、公式素材をそのままサイズ調整のみで使用する。
 
**デスクトップアプリ起動（プロトコルスキーム）：**
 
`protocol_scheme` フィールドに値が設定されているツールは、クリック時にデスクトップアプリ起動を優先し、失敗した場合は `url` へフォールバックする。
 
```javascript
function openLauncherApp(webUrl, protocolScheme) {
    if (!protocolScheme) {
        window.open(webUrl, '_blank', 'noopener,noreferrer');
        return;
    }
    const fallbackTimer = setTimeout(() => {
        window.open(webUrl, '_blank', 'noopener,noreferrer');
    }, 1500);
    window.location.href = protocolScheme;
    window.addEventListener('blur', () => clearTimeout(fallbackTimer), { once: true });
}
```

#### 3.2.2. ステータスカードエリア（全権限共通）
 
ランチャーエリアの下に、横並びのカード群を表示する。
 
| カード | 表示内容 | データソース |
|---|---|---|
| 本日の勤務状況 | 出勤前 / 勤務中 / 休憩中 / 退勤済 ＋ 出退勤時刻 | 02_打刻管理 |
| 今月の勤怠 | 提出ステータス（未提出 / 提出済 / 承認済 / 確定）＋ 出勤日数 | 03_勤怠管理 |
| 申請・承認 | 承認待ち件数・差し戻し件数をバッジで表示 | 05_稟議 |
 
- 各カードはクリックで対応機能ページへ遷移する。
- 勤務ステータスカードは状態に応じてアクセントカラーを変化させる（勤務中 = 左ボーダー青系）。
- グリッドは `repeat(auto-fill, minmax(240px, 1fr))` で実装し、スマートフォンでは自動的に1列縦並びになる。
#### 3.2.3. 権限別追加ウィジェット
 
`approver` 権限のユーザーには、ステータスカードエリアの下に以下のウィジェットを追加表示する。
 
| ウィジェット | 表示内容 |
|---|---|
| 承認待ち一覧ウィジェット | 自分が承認者に設定されている未処理申請の一覧（申請者・種別・提出日・件数）。クリックで `/portal/approval/` の該当申請へ遷移 |
| チームの勤怠状況ウィジェット | 自分の配下メンバー（`first_approver_id` が自分のユーザー）の当日出勤状況（出勤済 / 未打刻 / 有給）を一覧表示 |
 
> `approver` ウィジェットのデータは REST API で非同期取得し、ページ表示をブロックしない。取得中はスケルトンローディングを表示する。
 
#### 3.2.4. 機能タイルグリッド（全権限共通）
 
ステータスカードの下に、各業務機能へのナビゲーションタイルをグリッド表示する。
 
| タイル | アイコン | リンク先 | バッジ表示条件 |
|---|---|---|---|
| 打刻 | 🕐 | `/portal/timecard/` | 当日未打刻の場合にオレンジバッジ |
| 月次勤務表 | 📅 | `/portal/attendance/` | 月末が近く未提出の場合に警告バッジ |
| 交通費 | 🚗 | `/portal/expenses/` | 未入力日がある場合にバッジ（件数） |
| 申請・承認 | 📋 | `/portal/approval/` | 差し戻し件数バッジ |
| マイページ | 👤 | `/portal/profile/` | なし |
 
- グリッドは `repeat(auto-fill, minmax(160px, 1fr))` で実装する。
- スマートフォン（640px 以下）では `repeat(2, 1fr)` の2列固定とし、最小2列を保証する。
- 各タイルはアイコン・機能名・説明文・バッジで構成するカード型UIとする。ホバー時に `translateY(-2px)` の浮き上がりアニメーションを適用する。
- タイルの表示順は権限・状況に関わらず固定とする（パーソナライズ不可）。

#### 3.2.5. 外部ツールランチャー管理画面（wp-admin）
 
`hr_admin` / `administrator` 権限が wp-admin からランチャーのツール一覧を管理する。
 
**メニュー位置：** `ポータル設定 > 外部ツール設定`
 
**管理画面のレイアウト：**
 
- 左側に登録済みツール一覧（⠿ ハンドルによるドラッグ並べ替え対応）、右側に追加・編集フォームを配置する2カラムレイアウト。
- 一覧テーブルの列：アイコンプレビュー・ツール名・リンク先URL・起動方法・表示順・状態（表示中/非表示）・操作ボタン（編集）。
**管理画面の機能一覧：**
 
| 機能 | 詳細 |
|---|---|
| 一覧表示 | 登録済みツールを表示順に並べた表形式で表示 |
| 新規追加・編集 | 右側フォームからツール名・URL・アイコン画像・起動方法・表示順・表示状態を入力して登録・更新 |
| 並べ替え | ⠿ ハンドルのドラッグ＆ドロップで `sort_order` を変更。変更はランチャーバーに即時反映 |
| 有効/無効切り替え | 「表示する / 非表示にする」ラジオボタンで、削除せずに表示を一時停止できる |
| 削除 | 確認ダイアログを経て物理削除 |
 
**新規追加・編集フォームの入力項目：**
 
| フィールド | 必須 | 説明 |
|---|---|---|
| アイコン画像 | ✅ | PNG または SVG をアップロード（WordPress メディアライブラリを使用）。推奨サイズ 64px × 64px 以上、2MB 以内。プレビュー表示あり |
| ツール名 | ✅ | ポータル上のキャプション表示（50文字以内） |
| リンク先 URL | ✅ | 遷移先 URL（`https://` または `http://` で始まること） |
| 起動方法 | ✅ | 「別タブで開く」「デスクトップアプリを起動」の選択式 |
| デスクトップアプリ起動 URL | ― | 起動方法で「デスクトップアプリ」選択時に入力。プロトコルスキーム（例：`msteams://`）。設定した場合クリック時にアプリ起動を優先し、失敗時は上のリンク先 URL に切り替え |
| 表示順 | ― | 数値入力（ドラッグで変更した場合は自動更新） |
| バーへの表示 | ✅ | 表示する / 非表示にする（非表示にしてもデータは削除されない） |
 
**バリデーション：**
 
- ツール名は 50 文字以内。
- URL は `https://` または `http://` で始まること（サーバーサイドで正規表現チェック）。
- アイコン画像は 2MB 以内。PNG・SVG のみ許可。
- 同一 URL の重複登録は警告を表示するが保存はブロックしない（意図的な重複も考慮）。
**バー上プレビュー：**
 
- フォーム下部に「バー上のプレビュー」カードを表示し、保存後のアイコン・ラベル表示イメージを確認できるようにする。

### 3.3. バッジ通知（ヘッダー）
 
ポータル内通知は最小限とし、Google Chat に委譲できない「ポータル上での視覚的な作業残」の提示に限定する。
 
ヘッダー右エリアに 🔔 アイコンを設置し、以下の未処理件数の合計をバッジ数字で表示する。
 
| 通知種別 | 集計対象 |
|---|---|
| 差し戻し通知 | 自分の申請が差し戻しになった件数（05_稟議） |
| 承認待ち通知 | 自分が承認者として対応待ちの申請件数（`approver` のみ） |
| 打刻漏れ通知 | 当日未打刻（出勤前状態のまま16時以降）の場合に 1 件としてカウント |
 
- バッジ数字は 0 の場合は非表示とする。
- 🔔 アイコンのクリックで、対応する画面（差し戻しは `/portal/approval/`、打刻漏れは `/portal/timecard/`）へ遷移する（ドロップダウンリストは設けない）。
- バッジ件数はページロード時に REST API で取得し、以降は手動リロードで更新する（ポーリング・WebSocket は使用しない）。
---
 
### 3.4. スマートフォン対応方針
 
PC をメインターゲットとしつつ、以下の操作をスマートフォンで快適に行えることを保証する。
 
| 機能 | スマートフォン対応レベル |
|---|---|
| 打刻（`/portal/timecard/`） | フル対応・最優先（タップしやすいボタンサイズ、1画面で完結） |
| ダッシュボード（`/portal/`） | 表示・遷移のみ対応（ランチャー非表示・ウィジェットは縦積みレイアウト） |
| 月次勤務表（`/portal/attendance/`） | 閲覧対応・複雑な入力はPC推奨とし、スマートフォンでは読み取り専用ビューを提供 |
| 申請・承認（`/portal/approval/`） | 承認・差し戻し操作のみスマートフォン対応（新規申請はPC推奨） |
| 交通費（`/portal/expenses/`） | PC推奨・スマートフォンは参照のみ |
 
**レスポンシブブレークポイント：**
 
| ブレークポイント | 対象 | 主な変化 |
|---|---|---|
| `≥ 1024px` | PC レイアウト | 多列グリッド・ランチャー表示 |
| `640px ～ 1023px` | タブレット | グリッド列数を縮小 |
| `< 640px` | スマートフォン | ランチャー非表示・ステータスカード1列縦並び・タイル2列固定 |

## 4. アクセス制御・ルーティング
 
### 4.1. 認証ガード
 
`/portal/` 配下の全 URL に対し、WordPress のセッション有無を検証する認証ガードを設ける。
 
- 未認証ユーザーが `/portal/` 配下にアクセスした場合、`/portal/login/` へリダイレクトする。
- 認証済みでも `employment_status = 退職` のユーザーはポータルへのアクセスをすべて拒否し、ログイン画面にエラーメッセージを表示する。
- セッションタイムアウト後のアクセス時は `/portal/login/` へリダイレクトし、タイムアウトである旨をメッセージ表示する（元の URL は `redirect_to` パラメータで保持し、再ログイン後に復帰させる）。
### 4.2. 権限別アクセス制御
 
| 権限 | ポータルアクセス | 対応範囲 |
|---|---|---|
| `general_staff` | ✅ 許可 | `/portal/` 全機能（自分のデータのみ） |
| `approver` | ✅ 許可 | `/portal/` 全機能 ＋ 承認者ウィジェット表示 |
| `hr_admin` | ✅ 許可（自分のデータ操作のみ） | ポータル機能を一般社員と同様に利用可。管理操作は wp-admin で行う |
| `administrator` | ✅ 許可（自分のデータ操作のみ） | 同上 |
 
> `hr_admin`・`administrator` はポータルを「自分自身の勤怠・申請入力」にも利用するため、アクセスを完全禁止にしない。ただし管理用の追加ウィジェットや特権 UI はポータル内に設けない。
 
### 4.3. wp-admin との分離
 
- `general_staff` 権限が `wp-admin` にアクセスした場合、`init` フックで `/portal/` へ強制リダイレクトする（01_ユーザー管理モジュールで実装済み）。
- `approver` 権限も同様に wp-admin へのアクセスを禁止し、`/portal/` へリダイレクトする。
- ポータルの静的アセット（CSS・JS）は `wp_enqueue_scripts` で `/portal/` ページ判定時のみ読み込み、wp-admin への影響を排除する。

## 5. 実装方針（WordPress プラグイン構成）
 
### 5.1. プラグイン構成
 
本ポータル基盤は `ims-portal-core` プラグインとして実装し、各業務モジュールプラグイン（`ims-timecard`・`ims-attendance` 等）から共通基盤として利用される形とする。
 
```
ims-portal-core/
├── ims-portal-core.php
├── includes/
│   ├── class-portal-router.php
│   ├── class-portal-auth-guard.php
│   ├── class-portal-layout.php
│   ├── class-portal-badge.php
│   └── class-portal-launcher.php
├── templates/
│   ├── dashboard.php
│   └── layout.php
└── assets/
    ├── css/portal.css
    └── js/portal.js
```
 
### 5.2. ページ生成方式
 
- `/portal/` 配下の URL は WordPress の **カスタムエンドポイント**（`add_rewrite_rule` + `template_redirect`）で制御し、WordPress の固定ページには依存しない。
- 各モジュールプラグインは `ims_portal_register_page` アクションフックを呼び出すことで、ポータルルーターに自分のページを登録する。
```php
// 各モジュールプラグインの登録例（02_打刻管理）
add_action('ims_portal_register_page', function($router) {
    $router->register('/portal/timecard/', 'IMS_Timecard_Page');
});
```
 
### 5.3. バッジ件数取得 REST API
 
| エンドポイント | 用途 | 認証 |
|---|---|---|
| `GET /wp-json/ims/v1/portal/summary` | ダッシュボード全体のサマリー情報を一括取得 | WordPress セッション必須 |
| `GET /wp-json/ims/v1/portal/badge-count` | ヘッダーバッジの合計件数のみ取得（軽量） | WordPress セッション必須 |
 
`/portal/summary` のレスポンス例：
 
```json
{
  "attendance_status": "working",
  "clock_in": "09:05",
  "clock_out": null,
  "monthly_status": "submitted",
  "pending_approvals": 3,
  "returned_approvals": 1,
  "missing_timecard": false,
  "approver_widgets": {
    "pending_list": [],
    "team_today": []
  }
}
```
 
> `approver_widgets` フィールドは `approver` 権限以上のユーザーのみレスポンスに含める。

| エンドポイント | メソッド | 用途 | 認証 |
|---|---|---|---|

### 5.5. データベース設計（独自テーブル）
 
#### `wp_ims_launcher_apps`
 
```sql
CREATE TABLE wp_ims_launcher_apps (
    id               INT AUTO_INCREMENT PRIMARY KEY,
    app_name         VARCHAR(50)          NOT NULL,
    url              VARCHAR(2083)        NOT NULL,
    icon_url         VARCHAR(2083)        NOT NULL,
    protocol_scheme  VARCHAR(100)         DEFAULT NULL,
    sort_order       SMALLINT UNSIGNED    NOT NULL DEFAULT 0,
    is_active        TINYINT(1)           NOT NULL DEFAULT 1,
    created_by       BIGINT UNSIGNED      NOT NULL,
    created_at       DATETIME             NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at       DATETIME             NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_sort_active (is_active, sort_order)
);
```
 
**ポータル側での取得クエリ：**
 
```sql
SELECT id, app_name, url, icon_url, protocol_scheme
FROM wp_ims_launcher_apps
WHERE is_active = 1
ORDER BY sort_order ASC, id ASC;
```

## 8. 非機能要件
 
### 8.1. パフォーマンス
 
- ダッシュボード初期表示（HTML 描画）は **2秒以内** を目標とする。
- バッジ件数・ウィジェットデータは非同期取得とし、初期 HTML のレンダリングをブロックしない。
- ポータル共通 CSS・JS は minify してブラウザキャッシュを活用する。
### 8.2. セキュリティ
 
- 全 REST API エンドポイントに `permission_callback` を実装し、未認証リクエストを `401` で拒否する。
- 各エンドポイントはログインユーザー自身のデータのみ返却し、他ユーザーのデータを混入させない（`get_current_user_id()` で常に絞り込む）。
- CSRF 対策として、データ変更系のリクエストには WordPress nonce を使用する。
### 8.3. 保守性・拡張性
 
- 業務モジュールの追加時は `ims_portal_register_page` フックへの登録のみで済む設計とし、00_portal 本体の改修を不要にする。
- CSS カスタムプロパティによるデザイントークン管理で、ブランドカラー変更時の影響範囲を `portal.css` 1ファイルに限定する。
### 8.4. ブラウザサポート
 
| ブラウザ | サポート方針 |
|---|---|
| Chrome（最新2バージョン） | フルサポート |
| Edge（最新2バージョン） | フルサポート |
| Firefox（最新2バージョン） | フルサポート |
| Safari（最新2バージョン） | フルサポート（iOS Safari 含む） |
| Internet Explorer | **非対応** |
