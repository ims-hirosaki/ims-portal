# 要件定義書：02_打刻管理モジュール (02_time_tracking.md)
 
## 1. 目的・概要
 
本モジュールは、従業員の日々の出退勤・休憩のリアルタイム打刻ログを記録・管理する機能である。1日に複数回の休憩を許容し、各休憩の合計時間を実労働時間の計算に使用する。退勤時の打刻漏れ（休憩中ステータスのまま退勤・休憩を取ったが打刻しなかった）をその場で補完する UI/UX を提供し、労働基準法に準拠した正確な労働時間算出の土台となる。
 
打刻ログは **03_勤怠管理モジュール** が実労働時間を算出する唯一のデータソースとなり、**04_交通費モジュール** が通勤交通費を自動計算するトリガーともなる。
 
また、退勤打刻（`clock_out`）は **05_稟議モジュール** の残業申請乖離検知のトリガーとなる。乖離が検知された場合は **Google Chat Webhook** 経由でリアルタイム通知を行う。
 
---
 
## 2. マスター設定要件（プラグイン設定画面）
 
### 2.1. 打刻システム設定
 
`システム管理者（administrator）` のみが変更できるプラグイン設定画面（`設定 > 打刻システム設定`）に以下の項目を設ける。設定画面は以下の 3 セクションで構成する。
 
#### ① 深夜勤務の日付設定（内部: `date_boundary_hour`）
 
- **設定項目：** `date_boundary_hour`（整数・0〜23・初期値: `0`）
- **画面上の説明文：** 「日をまたいで勤務するスタッフがいる場合に設定します。通常の勤務形態のみの場合は 0 時のままで問題ありません。」
- **入力ラベル：** 「この時刻より前の退勤は『前日の勤務』として記録する」（単位：時、0〜23）
- **動作：** 退勤打刻の時刻がこの設定時刻より前（深夜帯）の場合、打刻ログの `work_date` を前日として記録する。
  - 例：`4` に設定した場合 → 深夜 0 時〜3 時 59 分の退勤は前日の勤務として集計される。
  - 初期値 `0`（日またぎ考慮なし）。
- **適用範囲：** 退勤打刻（`clock_out`）の `work_date` 判定にのみ使用する。出勤打刻は常に打刻日を `work_date` とする。
#### ② スタッフ自身による打刻の修正（内部: `staff_correction_level`）
 
スタッフ本人による打刻修正の許容範囲を、以下の 3 段階から選択する。人事担当者（`hr_admin`）・システム管理者（`administrator`）は設定に関わらず常に修正可能。
 
| 画面上の選択肢 | 設定値 | 動作 |
|---|---|---|
| 修正させない | `disabled` | スタッフ本人は修正不可。修正が必要な場合は管理者への依頼が必要。 |
| 当日分のみ修正できる | `today_only` | 当日の打刻に限り、スタッフ自身が修正できる。翌日以降は管理者のみ修正可能。 |
| 月次締めまでの分を修正できる | `pre_closing` | 当月の締め処理が完了するまでの間、スタッフ自身が過去の打刻を修正できる（初期値）。 |
 
#### ③ 残業アラートの通知先（Google Chat）
 
退勤打刻時の残業申請との乖離アラート（→ 3.3 参照）の通知先を設定する。稟議モジュール側の通知設定とは独立しており、打刻アラートの通知先チャットルームを稟議承認通知と分けて運用できる。
 
| 設定項目 | 画面上のラベル | 説明 |
|---|---|---|
| Webhook URL | 通知先のチャットルーム URL | 乖離アラートを送信する Google Chat ルームの Webhook URL |
| 乖離検知閾値 | ずれが何分以上でアラートを送るか | 申請の予定終了時刻と実退勤打刻の差がこの分数以上の場合に通知する（初期値: 30分） |
 
- Webhook URL 入力欄の横に「テスト送信」ボタンを設け、設定後すぐに疎通確認できるようにする。
- 通知の送信に失敗した場合も、打刻の記録自体には影響しない（最大 3 回自動再送）。

## 3. 機能要件
 
### 3.1. リアルタイム打刻機能
 
#### 打刻アクションの定義
 
フロント画面から以下の 4 種類のアクションを打刻する。
 
| アクション名 | `punch_type` 値 | 説明 |
|---|---|---|
| 出勤 | `clock_in` | 1日に1回のみ有効 |
| 休憩開始 | `break_in` | 1日に複数回可能 |
| 休憩終了 | `break_out` | 直前に `break_in` が存在する場合のみ有効 |
| 退勤 | `clock_out` | 1日に1回のみ有効 |
 
#### 1日の休憩管理（複数回対応）
 
- `break_in` → `break_out` の 1 セットを 1 回の休憩として記録する。
- 1日に何度でも繰り返すことができる（例：昼休憩・午後休憩など）。
- **実休憩時間の計算：** 当日の全 `break_out` 時刻から対応する `break_in` 時刻を引いた差の合計値を「総休憩時間」とする。
  ```
  総休憩時間 = Σ（各 break_out 時刻 − 対応する break_in 時刻）
  実労働時間 = clock_out 時刻 − clock_in 時刻 − 総休憩時間
  ```
- **→ 03_勤怠管理モジュールとの連携：** 本モジュールが記録した打刻ログから、上記式で実労働時間を算出する責務は 03_勤怠管理モジュールが持つ。
#### ステータス管理とボタン活性制御
 
ユーザーのリアルタイムステータスを `wp_attendance_logs` から動的に算出し、次に押すべきボタン以外を非活性化する。
 
| ステータス | 判定条件 | 活性ボタン |
|---|---|---|
| 出勤前 | 当日 `clock_in` なし | 【出勤】のみ |
| 勤務中 | `clock_in` あり・最終ログが `clock_in` または `break_out` | 【休憩開始】【退勤】 |
| 休憩中 | 最終ログが `break_in` | 【休憩終了】のみ（※退勤時の例外処理あり → 3.2 参照） |
| 退勤後 | 当日 `clock_out` あり | すべて非活性 |
 
#### サーバーサイド時刻の強制
 
- 打刻時刻はクライアント（PC・スマホ）の端末時刻を一切使用しない。
- WordPress サーバーの時刻（`current_time('mysql')` / タイムゾーン: Asia/Tokyo）をすべての打刻日時として記録する。

### 3.2. 退勤時の自動補完・確認ロジック
 
#### ケース A：休憩中ステータスのまま退勤ボタンを押した場合
 
ステータスが「休憩中」のとき【退勤】ボタンが押されると、エラーで弾かずに **休憩補完ポップアップ** を表示する。
 
**ポップアップの表示内容：**
- 休憩を始めた時刻（最終 `break_in` の `punched_at`）
- 出勤からの経過時間
- **労働基準法による休憩の目安（インフォボックス）：**
  - 勤務 6 時間以内 → 休憩の付与義務なし
  - 勤務 6 時間超〜8 時間以内 → 45 分以上の休憩が必要
  - 勤務 8 時間超 → 1 時間以上の休憩が必要
  - 経過時間に応じた具体的なメッセージ（例：「本日の勤務時間は 8 時間超のため、1 時間以上の休憩が推奨されます。」）を併記する。
- 実際に取った休憩時間の選択肢（以下の制約に従い表示）
**補完分数の逆転バリデーション（重要）：**
 
選択可能な最大分数 = `floor((現在時刻 − 最終 break_in 時刻) の分数)`
 
- 選択肢 A「45分」：`最大分数 ≥ 45` の場合のみ表示。ラベルに「6〜8時間勤務の法定最低ライン」と添える。
- 選択肢 B「60分」：`最大分数 ≥ 60` の場合のみ表示。8 時間超の勤務の場合は「推奨」バッジを表示する。
- 選択肢 C「その他の時間を入力」：常に表示。入力値が `最大分数` を超えた場合はリアルタイムでエラー表示してボタンを非活性化する。
- **すべての選択肢が表示できない場合（= 休憩開始直後に退勤しようとしている場合）** は、選択肢 C のみを表示し、「最大 ○分まで入力可能です」と案内する。
**確定操作（「休憩を登録して退勤する」ボタン押下）時のトランザクション処理：**
 
以下の 2 レコードをひとつのデータベーストランザクションで同時に保存する。どちらか一方でも失敗した場合はロールバックし、ユーザーにエラーを通知する。
 
1. **休憩終了補完ログ：** `punch_type = break_out`・`punched_at = 最終 break_in 時刻 + 選択された分数`・`is_auto_filled = 1`
2. **退勤ログ：** `punch_type = clock_out`・`punched_at = 現在時刻（サーバー時刻）`・`is_auto_filled = 0`
---
 
#### ケース B：休憩を一度も打刻せずに退勤した場合
 
「出勤打刻はあるが当日 `break_in` が 0 件」の状態で【退勤】ボタンが押された場合、以下のロジックを適用する。
 
- **実勤務時間（`現在時刻 − clock_in 時刻`）が 6 時間以下：** ポップアップなし。そのまま退勤を記録する。
- **実勤務時間が 6 時間超：** 確認ポップアップを表示する。
**確認ポップアップの構成：**
- 出勤時刻・現在の勤務時間を表示する。
- **労働基準法による休憩の目安（インフォボックス）：**
  - 勤務 6 時間以内 → 休憩の付与義務なし
  - 勤務 6 時間超〜8 時間以内 → 45 分以上の休憩が必要
  - 勤務 8 時間超 → 1 時間以上の休憩が必要
  - 現在の勤務時間に応じた具体的なメッセージ（例：「現在 7 時間 28 分のため、45 分以上の休憩が必要です。」）を併記する。
- ボタン A：「休憩を登録して退勤する」→ ケース A と同じ補完分数選択 UI を表示する。
- ボタン B：「休憩なしで退勤する」→ 休憩補完なしで `clock_out` のみ記録する。
- ボタン B の下部に「休憩なしで退勤を選択した場合も退勤は完了します。休憩の登録はシステムでは強制しません。」と明記する。
> **労基法の補足：** 法定の休憩付与義務（6時間超 → 45 分以上、8時間超 → 1 時間以上）への準拠はデータを記録することで管理者が確認できる状態とする。強制的に休憩を登録させる仕様とはしない。

### 3.3. 退勤打刻時の残業乖離アラート通知
 
退勤打刻（`clock_out`）が記録された際に、**05_稟議モジュール**と連携して残業申請との乖離チェックを行い、閾値を超えた場合に Google Chat Webhook 経由でアラートを通知する。
 
#### 乖離検知フロー
 
1. `clock_out` 打刻が `wp_attendance_logs` に記録される。
2. 当該ユーザー・当該 `work_date` に `confirmed` 状態の残業申請（05_稟議モジュール）が存在するか確認する。
3. 存在する場合、`clock_out.punched_at` と `wp_approval_meta.overtime_end_time`（残業申請の予定終了時刻）を比較する。
4. 差異がプラグイン設定の乖離検知閾値（デフォルト: **30 分以上**）を超えた場合、Google Chat Webhook 経由でアラートを送信する。
#### アラート通知内容
 
```
【残業時間のずれを検知しました】
申請者 : ○○ ○○
対象日 : 2025年6月15日
申請の予定終了 : 18:00
実際の退勤打刻 : 19:32（＋1時間32分）
勤怠集計は実際の打刻時刻を正として反映します。
```
 
**通知先：** 申請者・承認済みの承認者（全員）にそれぞれ Google Chat Webhook 通知を送信する。
 
#### 通知の失敗処理
 
- 最大 3 回リトライする。3 回失敗した場合はエラーを WordPress `error_log` に記録する。
- 通知失敗は打刻記録自体をブロックしない（通知はベストエフォート）。
> **実打刻優先の原則：** 残業申請は承認記録（`overtime_approved` フラグ）として 03_勤怠管理モジュールに反映されるが、実際の労働時間計算は本モジュールの打刻ログを唯一の正とする。

### 3.4. 打刻修正機能
 
#### 修正許可レベルの動作
 
プラグイン設定の `staff_correction_level`（→ 2.1 参照）に応じて、フロント画面の修正ボタンの表示・操作可否を制御する。
 
| 操作者 | `disabled` | `today_only` | `pre_closing`（デフォルト） |
|---|---|---|---|
| スタッフ本人 | 修正ボタン非表示 | 当日分のみ修正可 | 締め前全日分を修正可 |
| `approver` | 修正ボタン非表示 | 修正ボタン非表示 | 修正ボタン非表示 |
| `hr_admin` / `administrator` | 常に直接修正可 | 常に直接修正可 | 常に直接修正可 |
 
**「締め後」のロック：** `wp_monthly_summary`（03_勤怠管理モジュール）のステータスが `確定` となった月度の打刻データは、すべての操作者に対して修正不可（読み取り専用）とする。
 
#### 修正操作の手順
 
1. 打刻履歴一覧の対象行の「修正」ボタンをクリック。
2. 修正フォームを表示（修正前の打刻日時・新しい打刻日時・修正理由の入力欄）。
3. 修正理由は必須入力とする。
4. 保存時に `wp_attendance_corrections` テーブルへ修正前後の値を記録した後、`wp_attendance_logs` の当該レコードを新しい打刻日時で上書き更新する。
5. 修正後に日次のステータス整合性チェックを実行し、矛盾（例：`clock_in` > `clock_out`）がある場合はエラーを返す。
#### 修正履歴の記録
 
修正が行われるたびに `wp_attendance_corrections` テーブルに以下を記録する（監査証跡）。修正履歴は削除不可とする。
 
---
 
### 3.5. 打刻ログデータ保持
 
- 打刻ログはカスタムテーブル `wp_attendance_logs` に記録する（大量ログの WordPress 標準テーブルへの混在を防ぐため）。
- **保持期間：** 労働基準法第 109 条に基づき、最低 **5 年間** 保持する。削除機能は管理画面に設けず、定期的なアーカイブ対応は別途インフラ側で実施する。

## 4. 画面要件（UI/UX）
 
### 4.1. フロントエンド：打刻コンソール（`/portal/timecard/`）
 
完全レスポンシブ（スマートフォン・PC 対応）で構築する。WP REST API を介した非同期（Fetch API）で打刻処理を行い、ページ全体のリロードなしにボタン状態を切り替える。
 
#### 表示要素
 
- **現在日時：** 1 秒ごとに `setInterval` でカウントアップ表示（UI クロック）。打刻時刻はサーバー時刻を使用するため、UI クロックはあくまで参考表示であることをラベルで明示する。
- **現在のステータス：** 「出勤前 / 勤務中 / 休憩中 / 退勤済」をカラーバッジで視認しやすく表示。
- **本日の実勤務時間（経過）：** `現在時刻 − clock_in 時刻 − 総休憩時間` を表示。1 分ごとに更新。
- **打刻ボタン（4種類）：** ステータスに応じて活性/非活性を制御（→ 3.1 参照）。
#### 打刻履歴テーブル
 
当月の打刻記録を **1 日 1 行・横並び形式** で表示する。月送り（`‹ ›`）ボタンで過去月も参照できる。
 
| 列 | 内容 |
|---|---|
| 日付 | MM/DD（曜日）。土曜は青・日曜は赤で表示 |
| 出勤 | `clock_in` の時刻 |
| 休憩開始 | `break_in` の時刻。複数回ある場合はセル内に縦並びで全件表示。2 回以上の場合はセル下部に合計休憩時間を表示 |
| 休憩終了 | `break_out` の時刻。休憩開始と同様に全件縦並び表示 |
| 退勤 | `clock_out` の時刻 |
| 実労働 | 実労働時間（分単位で計算・時間表示） |
| 操作 | 修正ボタン（修正許可レベルに応じて表示・非表示） |
 
- 打刻がない列は「—」で表示する。
- システムによる自動補完打刻には「自動補完」タグ（黄色）を時刻の隣に表示する。
- 今日の行は背景色（薄黄）でハイライトする。
#### 打刻修正（スタッフ）
 
修正ボタン押下でポップアップを表示する。
 
1. 対象日・現在の打刻時刻を表示する。
2. 修正後の日時（必須）・修正理由（必須）を入力する。
3. 「修正を登録する」押下後、① 修正内容を記録 → ② データベースを更新 → ③ 画面に反映 の 3 ステップをアニメーション表示してからテーブルを再描画する。
#### GPS 位置情報のオプトイン
 
- スマートフォンのブラウザからアクセスした場合、初回打刻時にブラウザネイティブの位置情報許可ダイアログを表示する（Geolocation API）。
- 許可した場合：緯度・経度を取得し打刻ログに付与する。
- 拒否した場合：位置情報なし（`NULL`）で打刻を完了する。打刻自体はブロックしない。
- PC からのアクセスでは位置情報取得を試みない。
#### 多重サブミット防止（クライアント側）
 
- ボタン押下直後に JavaScript で即時 `disabled` 属性を付与し、API レスポンスが返るまで再押下できないようにする。
- 通信失敗（ネットワークエラー・タイムアウト）時はエラーメッセージを表示し、ボタンの `disabled` を解除して再試行できる状態に戻す。打刻が完了したとユーザーが誤認しないよう、送信中・成功・失敗の状態を明示的に表示する。

### 4.2. 管理者向け：打刻ログ照会画面
 
- メニュー階層：`社員管理 > 打刻ログ照会`（wp-admin 内）
- **画面の目的：** 全社員の打刻記録を横断的に調査・証跡確認するための監査用画面。日常的な打刻修正には使用しない。想定利用シーンは以下の通り。
  - 労働基準監督署の調査対応
  - 特定の打刻に疑義が生じたとき
  - 自動補完された打刻の確認
  - 過去の修正履歴の証跡確認
- **検索結果表示方式：** 画面を開いた直後は検索フォームのみ表示し、結果は表示しない。「検索する」ボタン押下後に結果テーブルを表示する。条件を指定せずに検索した場合は全件を表示する。
- **検索・フィルター：** 社員名 / 社員番号 / 対象期間（開始〜終了）/ 打刻の種類 / 自動補完 / 修正履歴の有無 でフィルタリング可能。
- **表示列：** 社員名・対象日・打刻の種類・打刻時刻（修正済みの場合は「修正あり」タグを表示）・自動補完・GPS（有無）・接続元 IP・修正ボタン。
- **修正履歴の表示：** 各ログ行をクリックすると展開し、修正履歴（修正前後の値・修正者・修正日時・修正理由）を確認できる。修正履歴がない場合はその旨を表示する。
- **修正操作：** 人事担当者・システム管理者はスタッフ側の修正許可設定に関わらず直接修正可能。修正理由を必須入力として修正履歴を記録する。

## 5. データベース設計（独自テーブル）
 
### 5.1. `wp_attendance_logs`（打刻ログ）
 
```sql
CREATE TABLE wp_attendance_logs (
    log_id         INT AUTO_INCREMENT PRIMARY KEY,
    user_id        BIGINT UNSIGNED NOT NULL,         -- 01モジュール wp_users.ID を参照
    work_date      DATE            NOT NULL,          -- 帰属日付（日またぎ設定を考慮して決定）
    punch_type     ENUM('clock_in','break_in','break_out','clock_out') NOT NULL,
    punched_at     DATETIME        NOT NULL,          -- サーバー時刻（Asia/Tokyo）
    is_auto_filled TINYINT(1)      NOT NULL DEFAULT 0, -- 1 = 自動補完されたレコード
    ip_address     VARCHAR(45)     DEFAULT NULL,      -- グローバルIPアドレス
    gps_latitude   DECIMAL(10,7)   DEFAULT NULL,      -- GPS緯度（任意・オプトイン）
    gps_longitude  DECIMAL(10,7)   DEFAULT NULL,      -- GPS経度（任意・オプトイン）
    note           TEXT            DEFAULT NULL,      -- 備考
    created_at     DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_user_date  (user_id, work_date),
    INDEX idx_punched_at (punched_at)
);
```
 
**制約・ルール：**
- 同一ユーザーの同一 `work_date` に `clock_in` は 1 件のみ許容する。アプリケーション層で制御する。
- 同一ユーザーの同一 `work_date` に `clock_out` は 1 件のみ許容する。アプリケーション層で制御する。
- `break_in` / `break_out` は複数件許容する。
### 5.2. `wp_attendance_corrections`（打刻修正履歴）
 
```sql
CREATE TABLE wp_attendance_corrections (
    id                 INT AUTO_INCREMENT PRIMARY KEY,
    log_id             INT             NOT NULL,   -- wp_attendance_logs.log_id を参照
    original_datetime  DATETIME        NOT NULL,   -- 修正前の punched_at
    corrected_datetime DATETIME        NOT NULL,   -- 修正後の punched_at
    reason             TEXT            NOT NULL,   -- 修正理由（必須）
    corrected_by       BIGINT UNSIGNED NOT NULL,   -- 修正操作者のユーザーID
    corrected_at       DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_log_id (log_id)
);
```
 
**制約・ルール：**
- 本テーブルのレコードは削除不可（監査証跡）。
- 複数回修正された場合は修正ごとに 1 行追記される。

## 7. 非機能要件・セキュリティ
 
### 7.1. 多重サブミット防止（サーバーサイド）
 
クライアント側の `disabled` 制御に加え、サーバーサイドでも以下のチェックを行う。
 
- 同一ユーザー・同一 `punch_type`・直近 **5 秒以内** に同一 `punch_type` のログが存在する場合、`409 Conflict` を返してレコードの重複挿入を防ぐ。
- これにより、JavaScript が無効な環境や API への直接リクエストによる二重登録を防止する。
### 7.2. CSRF 対策・REST API 認証
 
- WP REST API カスタムエンドポイント（打刻・修正）には `permission_callback` を実装し、未認証リクエストを拒否する。
- フロントエンドのフォームには WordPress nonce（`wp_create_nonce`）を埋め込み、API 側で `check_ajax_referer` または REST API nonce 検証を行う。
### 7.3. GPS データのプライバシー保護
 
- GPS データ（緯度・経度）は打刻ログの一部として `wp_attendance_logs` に保存する。
- 閲覧権限は打刻ログ全体と同じ（本人は自身のログのみ、管理者は全員分）とする。
- GPS データの収集は個人情報保護法に基づくオプトイン方式とし、収集目的（不正打刻防止・テレワーク管理）を利用規約またはシステム内の案内文で明示する。
### 7.4. Google Chat 通知の信頼性
 
- Webhook リクエストは最大 **3 回リトライ**する（リトライ間隔: 指数バックオフ）。
- 3 回失敗した場合は WordPress `error_log` にエラー内容を記録し、管理者向けシステム通知を発行する。
- 通知の失敗は打刻記録自体をブロックしない（通知はベストエフォート）。
- 将来的な Gmail フォールバック通知（06_Google Workspace 連携 6.8節）への拡張ポイントを実装上に設ける。
### 7.5. データ保持・削除制限
 
- `wp_attendance_logs` および `wp_attendance_corrections` の物理削除は管理画面から実行できない。
- 削除が必要な場合はデータベース直接操作とし、操作ログを別途残す運用とする。
