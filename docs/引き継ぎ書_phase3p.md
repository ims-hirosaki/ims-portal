## 2. 確定済みアーキテクチャ方針（Phase 3f 版からの差分のみ）

- **コアに手を入れた箇所が3つある（いずれもユーザー確認済みの例外）。** コアはモジュールを知らない原則は守っている。
  1. **タイルバッジの色**：`TileRegistry::add()` の `badge` は文字列（従来どおり朱）か、
     `['text' => '…', 'tone' => 'neutral'|'warning'|'danger']`（グレー／金／朱）を返せる。色は `assets/css/tile-badge.css`。
  2. **wp-admin の限定開放**：`general_staff` / `approver` は wp-admin に入れないが、各モジュールが
     `ims_wp_admin_limited_access` フィルタで `['pages' => [...], 'actions' => [...]]` を返した画面（`admin.php?page=`）と
     処理（`admin-post.php` の action）だけは通す（`AuthGuard` ＋ 純粋関数 `AdminAccessPolicy`）。今は 03 が approver に
     月次提出状況・勤務表の確認・チェック承認・差し戻し・印刷だけを許可している（`Attendance\AdminMenu::limited_access()`）。
  3. **有効化の順序**（`ims-portal.php`）：有効化フックは `IMS_Portal_Plugin::activate()` で、`boot()` → `Installer::activate()` の順。
     `boot()` は1リクエスト1回だけ（`$booted`）。§4① 参照。
- **管理メニューは 00 §4.4 の表が正本。** 新しい管理画面は、まず表に行を足してから実装する。親メニュー「勤怠管理」「共通マスタ」は
  `Attendance\AdminMenu` が登録し、**親メニュー自体を先頭の画面にしている（スラッグ＝先頭画面）ので、画面URLは親を変えても変わらない。**
- **「提出済みなら確定値、未提出なら参考値」の判定は `MonthlyStatementCalculator::totals()` に一本化**した。
  集計表タブ・印刷用勤務表はこれを使う。新しく月次の数字を出す画面を作るときも必ずこれを使う（二重実装しない）。

## 4. 今回判明した重要な落とし穴・設計判断

### ① 有効化フックはモジュール初期化より先に走る（修正済み。#34）
有効化の処理は `plugins_loaded` より後、プラグインを読み込んだその場で走る。そのため、以前は `boot()` 未実行のまま
`Installer::activate()` が動き、**テーブルが1つも作られないのに `ims_db_version` だけ最新になっていた**
（新しい環境での初回有効化・無効化→再有効化で発生。WordPress 6.8 の実環境で再現・修正を確認）。
本番はファイル上書き → `admin_init` の `maybe_upgrade()` で追従しているので、影響は無かった。

### ② `Installer::run_migrations()` は DDL の失敗を見ない（未修正）
SQL がエラーでも `ims_db_version` は上がる（`引き継ぎ書_phase3f.md` §2 の問題のうち、①とは別のもの）。
「テーブルが実際にできたか確かめてから上げる」ように直す案はユーザーに提示済みで、まだ依頼は無い。
**DB_VERSION を上げたデプロイ後は、引き続きテーブル・列の実在を確認すること。**

### ③ approver は wp-admin に原則入れない（00 §4.3）
approver 向けの機能を wp-admin に作るときは、`ims_wp_admin_limited_access` で画面と処理を**両方**許可する必要がある
（許可しないと `/portal/` に戻される）。WordPress は admin_init より前にページの権限を見るので、権限の無い画面は 403 になる。

### ④ 月次の数字の「確定値／参考値」
提出済み以降（submitted / checked / confirmed）は `wp_monthly_summary.total_*`（提出時の値）、
未提出・差し戻し中は今の入力から計算した参考値。画面には「未提出のため参考値」と明記する。

### ⑤ 集計のルール（要件定義書に追記済み。ユーザー確認済み）
- **週次の法定外残業**（03 §3.1）：日曜始まり。締め期間をまたぐ週は期間内の日だけ。打刻由来の実働 − 日次法定外で数える。
  有給・時間休・半日休の加算分と、**休日出勤の日は週40hに数えない**。週次法定外になった分は**法定内残業から差し引く**（二重計上の解消）。
- **出勤日数**：フラグなしの日は出勤打刻（clock_in）がある日だけ数える。
- **給与スナップショットの「対象月末日」**（03 §3.5）：年月ラベルの**カレンダー上の月末**（締め日にはそろえない）。
- **欠勤日数**：稼働日カレンダーが無いため**常に0**（CSV・集計表とも）。弥生側で手入力する。

### ⑥ 確定の取り消し（03 §3.5・§7.3 に例外として追記）
テスト運用のための機能。**本番運用に入ったら「ポータル設定 > 確定の取り消し」をオフにする**ことをユーザーに伝えてある。
戻し先は「本人に差し戻す（rejected_by_admin）」か「最終承認だけやり直す（checked）」。取り消すと `final_approved_*` と `snapshot_*` は空に戻る。

## 6. テスト環境の作り方（今回確立。次回も使える）

このクラウド環境で、**本物の WordPress 6.8 + MariaDB** を立てて確認できる（スタブでは分からない不具合を今回2件見つけた）。

```bash
# MariaDB（入っていなければ apt で入る）
apt-get install -y mariadb-server && service mariadb start
mariadb -e "CREATE USER IF NOT EXISTS 'wp'@'localhost' IDENTIFIED BY 'wp'; CREATE DATABASE wptest CHARACTER SET utf8mb4; GRANT ALL ON wptest.* TO 'wp'@'localhost';"

# WordPress 本体：wordpress.org はネットワーク設定で拒否される。GitHub の公式ミラーを clone する
GIT_LFS_SKIP_SMUDGE=1 git clone --depth 1 --branch 6.8-branch https://github.com/WordPress/wordpress <作業用ディレクトリ>/wp
# WP-CLI は GitHub から取得できる（root なので --allow-root が必要）
curl -sSL -o wp-cli.phar https://raw.githubusercontent.com/wp-cli/builds/gh-pages/phar/wp-cli.phar
php wp-cli.phar --allow-root --path=wp config create --dbname=wptest --dbuser=wp --dbpass=wp --dbhost=localhost --skip-check
php wp-cli.phar --allow-root --path=wp core install --url=http://127.0.0.1:8088 --title=t --admin_user=admin --admin_password=admin --admin_email=a@example.com --skip-email
ln -s /home/user/ims-portal wp/wp-content/plugins/ims-portal
php wp-cli.phar --allow-root --path=wp plugin activate ims-portal
( cd wp && php -S 127.0.0.1:8088 )   # 画面の確認用
```

- ログイン状態でのアクセスは、`wp eval-file` で `wp_generate_auth_cookie()` を作って curl / Playwright に渡すと早い。
- Chromium（Playwright）は最初から入っている。印刷の1ページ収まりは `page.pdf()` と `emulateMedia({media:'print'})` で確認した。
- **スモークテストはリポジトリに入れていない**（今回もセッションの作業用ディレクトリに置いたため、セッション終了で消える）。
  必要なら `tests/smoke/` を作ってコミットする運用をユーザーに相談するとよい。
